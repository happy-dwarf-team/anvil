# The Manager installs the team's plugins from a reviewed catalog, on the player's click

A player who has Anvil does not learn from it which plugins exist, and installing one from a release zip or the Workshop needs knowledge the player may not have. The Manager gets a **Catalog** tab with the team's plugins (Bellows, Tongs, Hamweard, Mei) and an **Install** button. Until now Anvil downloaded nothing and the Manager's release check only showed a link (design §19), so this is a change of the security rules.

- **The list.** `catalog/plugins.json` in this repository lists each plugin with a short summary, its page, its Workshop item, the game builds and the Anvil range it declares, whether it affects gameplay, and **one pinned release**: the version, the zip's URL on `github.com/happy-dwarf-team/<repo>/releases/download/`, its size and its SHA-256. The Manager carries the copy of its own build and shows it without the network. **Get the current list** fetches the file from `main` (`raw.githubusercontent.com`) on the player's click; a list that does not validate, or has a newer schema, is refused and the Manager keeps the one it has.
- **Install.** On a click and a confirmation that names the file, its size and where it comes from, the Manager downloads the pinned zip and refuses it unless its size and SHA-256 equal the pin. Then the zip takes the path a zip from the picker takes: it is checked with `anvil check`'s own code against the game's `eu4.exe`, the player sees the same dialog (version, authors, gameplay, problems, the native-code warning, whether the loader would skip it) and confirms again. The id and version in its `plugin.toml` must equal the entry.
- **Trust.** The pin is what the Manager trusts, not the release: the release's `SHA256SUMS.txt` sits beside the zip, so whoever replaces one replaces both, and TLS already protects the transfer. An entry changes only through a pull request to this repository (branch protection, required checks), and the `catalog` job of CI downloads every pinned zip, compares the size and the hash, runs `gh attestation verify --repo happy-dwarf-team/<repo>` (the build provenance the plugin's own release workflow attached) and compares `plugin.toml` and `symbols.toml` in the zip with the entry. So every pin is a build of the plugin's release workflow, verified once with GitHub's own tool, and the Manager only compares bytes.
- **Consent.** Nothing reaches the network without a click: **Get the current list** and **Install**. The list is not fetched at start, not even when the release check is on. The Workshop link only opens Steam's page of the item in the browser. *Superseded in part by [ADR 0006](0006-catalog-check-at-start.md): with the release check on, the Manager reads the list once at start; a zip is still downloaded only on the player's click.*
- **Whose plugins.** Only the team's: a download URL outside `github.com/happy-dwarf-team/` does not validate. Plugins of other authors need a policy for reviewing them first.

## Considered options

- *Fetch the latest release, check it against its `SHA256SUMS.txt` and verify the attestation in the Manager.* Rejected. The sums come from the same release as the zip and add nothing over TLS. Verifying a Sigstore bundle in the Manager means X.509 chains to Fulcio, ECDSA, Rekor inclusion proofs and a trust root that changes, a large amount of security-critical code next to a tool that already does it (`gh attestation verify`). And "latest" installs whatever was published a minute ago, before anyone looked.
- *The list on anvil.happydwarf.dev* (its `plugins.json`, which the site's plugin cards use). Rejected for the pins: the site is built from the GitHub API on every release, so a hash there would be copied, not reviewed, and it lives in another repository. The site keeps its file for the cards.
- *Only the copy built into the Manager.* Rejected as the only source: a plugin release would wait for the next Anvil release to reach the tab. It stays the list the tab shows before the player fetches one.
- *Subscribing to the Workshop item from the Manager.* Rejected: it needs the Steamworks API in the Manager and a running Steam client; a link does the same with Steam's own confirmation.

## Consequences

- Each plugin release is followed by a pull request `chore(catalog): <id> <version>`, written by `catalog/update.py <id>`. Its type is hidden, so it starts no Anvil release: players get it with **Get the current list**, and the built-in copy follows with the next Anvil release.
- The pins lag behind releases until that pull request is merged; the Manager never offers a release CI has not verified.
- Mei's zip has no fonts (the game reads them from a mod's `gfx/fonts/mei/`), so its entry says the Workshop item carries both. The tab also links each plugin's page.
- A list from `main` reaches every Manager that fetches it, old ones included: a new field is ignored by an older Manager, and a change it would misread raises `schema`, which older Managers refuse.
- *Added in 1.20 ([ADR 0010](0010-plugin-translations.md)):* an entry's `translations` gives its summary and note in each language of the Manager, by the codes of `ANVIL_LANGUAGE`; the Manager shows the player's language's and English otherwise, an older Manager ignores the field, and the `catalog` job requires every language.
