# Settings belong to modules, and the overlay writes switches and opt-ins

Status: **accepted** (2026-11-14). The maintainer accepted every point on 2026-11-14, point 10 after trying prototype B5. Follows [ADR 0011](0011-plugin-modules.md) and the player UI guidelines ([ui-guidelines.md](../ui-guidelines.md)).

ADR 0011 gave a plugin modules, each with its own switch and opt-ins in `anvil.toml`. Settings stayed the plugin's: `settings.toml` (design §5.3) knows a `group`, which is only a subheading. The Manager therefore shows module switches on its Plugins tab and settings on a separate Settings tab, and the overlay shows modules read-only and settings in a list of their own. A player who wants to know what a module does with its options has to match names by hand. Plugins filled the gap with their own conventions: Bellows on `main` has a mode setting named as each of its 23 modules (on / off / verify), so the same feature has two switches, and the module's "on" with the setting's "off" leaves it off; Tongs has `game_calls_ironman` and `game_calls_multiplayer` settings beside the core's opt-ins. The guidelines settle the UI as one tree (plugin, modules, their settings) drawn the same way in both apps. This ADR decides what the core, the files and `anvil.control` need for that.

How to read the evidence. **[code]**: read in this repository or a team plugin. **[prototype]**: the throwaway page `tools/manager/prototype/module-switches.html` (branch `prototype/module-switches`, variants B4 and B5), built on the real manifests of 15 plugins on 2026-11-14 and two sample plugins from mods. **[hypothesis]**: not checked.

## Decision

### Files

1. **A setting may name its module.** `settings.toml` gets an optional `module = "<id>"` on a setting. The id must be declared in the plugin's `[[modules]]`; anything else is a schema error, which skips the plugin as any other (design §5.3) and which `anvil check` reports at its line. A setting without `module` belongs to the plugin. Both apps draw a module's settings under the module and the rest under the plugin; `group` stays a subheading inside either.
2. **A setting may be advanced.** An optional `advanced = true` (default `false`) folds the setting behind "Advanced (n)" under its module or plugin. It is for author and lab options. A magic group name was the alternative and would not survive translation.
3. **A module may name its group.** `[[modules]]` gets an optional `group`: a subheading in the order of its first module, like a setting's group. It changes nothing but the drawing.
4. **A setting can retire into a module, and the core moves the player's choice.** `settings.toml` may list `[retired.<name>]` with `module = "<id>"` and `off = [<values>]`: a setting that an earlier version had and that the module's switch replaces. At the start, before it resolves modules, the core reads the player's file; when it holds that name with a value in `off`, the core adds the module to `disabled_modules`, removes the value from the player's file and logs both. The module is off at that same start. Any other value of a retired name is removed as well. Without this, a value the plugin no longer declares is ignored (design §11), the module's `default` applies, and a feature the player had turned off comes back on. A plugin never writes `anvil.toml` itself (point 6).
5. **No setting repeats a switch.** `anvil check` warns when a setting's name equals a module id. A guess from labels ("Enable …") was considered and left out: it would warn on settings that are fine.

### Writing and state

6. **One writer at a time.** While EU4 runs from a folder, the overlay is the only writer of its `anvil.toml`, `trust.toml` and the players' settings files, through `anvil.control`; the Manager is read-only for that folder, as it already is for its own operations [code: `manager_app.cpp`, `read_only()`], and reads the files again when the game exits [hypothesis: not checked whether it does today]. The core writes `anvil.toml` only for point 4, before any plugin loads and before the overlay can.
7. **The overlay writes switches and opt-ins.** `anvil.control` gets appended calls, after the existing ones (it is private, ADR 0001): set a plugin's or a module's switch (`disabled_plugins`, `enabled_modules`, `disabled_modules`) and set an opt-in (`allow_ironman`, `allow_multiplayer`), each for a key `<plugin>` or `<plugin>.<module>`. They write `anvil.toml` atomically, as the settings calls write the player's file (design §11), and take effect at the next start; the running game does not change. Each call answers with the state at the next start, so the overlay marks it. The overlay refuses to turn off `anvil-overlay` and every plugin it needs (today `anvil-game`), with "turn it off in Anvil Manager"; the Manager allows it, with the plugins that stop with it named next to the switch.
8. **The core records what a start used.** At each start the core writes `anvil/data/anvil/last-start.toml`: the lists of `anvil.toml`, the approvals of `trust.toml` and the values of every plugin's settings as that start read them. The Manager compares the files with it to mark "at the next start" and to undo, also while the game is closed; the overlay asks `anvil.control`, which has the same in memory. A missing or unreadable record means nothing is marked [hypothesis: the file is small; not measured].
9. **One view model for both apps.** `src/ui/` gets a model that takes a snapshot (plugins, modules, settings with their saved, current and default values, approvals, the record of point 8, the dependency graph) and gives back what the player changed as a list of edits. The Manager builds the snapshot from the files through `anvil_core` and applies edits with `write_player_settings` and its `anvil.toml` writer; the overlay builds it from `anvil.control` and applies edits through it. Rules that are not drawing (what loads, what a dependency chain turns on, what is pending, what a reset changes, what the search and the filter chips of `docs/ui-guidelines.md` §5 match) live in the model and are unit-tested there.

### What the player sees

10. **Plugins from mods are in the same list, and the Mods tab goes** (prototype B5).
    - A third section "From mods" follows the player's own plugins: "3 plugins in 3 enabled mods, 2 wait for approval, 1 cannot load".
    - **What waits for the player is visible from every tab.** The Plugins tab's label carries "2 to approve", and the tab opens with a line naming each plugin that waits, first approvals and updates alike ("Trade Tweaks (update to 1.1.0)"), each a button that selects it. The list entry of an update says "update waits for approval" and "1.0.2 runs until you approve 1.1.0"; the version shown is the one that runs.
    - The detail of a plugin waiting for its first approval shows the facts of design §14 (mod, Workshop item, authors, source, what changes the game, game addresses, folder hash), its modules greyed, and "Approve..." with the confirmation the Manager has today. One with an update waiting shows the same above its normal controls, since the approved copy runs. An approved plugin from a mod has "Revoke approval..." under its name, and no Remove.
    - What only the Mods tab shows today moves with it [code: `manager_app.cpp` `draw_mods_tab`, overlay `draw_mods`]: a plugin that cannot load (invalid, conflict, a local plugin with its id loads instead) is an entry with its state word and the reason in its detail, other mods with the same id included; the playset (enabled mods, a missing or unreadable `dlc_load.json` or descriptor) is the section's heading and a warning line above the list; "Check again" becomes the Manager's refresh of the Plugins tab. The catalog's warning against a plugin that presents itself as another stays in the approval's confirmation.
11. **Dependencies.** A plugin whose dependency does not load is greyed in the list with "off: needs Mei", and its detail says through what ("Needs Mei (through Anvil Map), which is off") with a button that turns the missing plugins on. Turning on a plugin whose dependencies are off asks first and names the whole chain, dependencies first, each with what needs it ("Turn on 3 plugins": Mei, Anvil Map, Tongs). A plugin others need says so next to its switch ("Needed by Anvil Map. Turning it off stops it too."). Dependents keep their own switches; nothing is turned off for them.
12. **Defaults and reset.** Every setting's "(?)" names its default; a changed value is marked "changed" with "default: <value>" and a Reset button (no confirmation: it is one value, shown before the click). A module with changed settings offers "Reset settings (n)...", and a plugin with any change "Reset to defaults...": both confirm with the list of what changes, old value to new. A plugin's reset covers its settings, its modules' switches and its opt-ins; never its own switch, and never an approval. `ANVIL_CONTROL_VALUE_DEFAULT` already gives the default [code: `anvil_control.h`], so no call is added for it.
13. **Screenshots by command line.** The Manager gets a screenshot mode for the guidelines' checklist: `AnvilManager.exe --screenshot <out-dir> --lang <code> --scale <percent> [--tab <name>] [--select <plugin>]` draws the window from a folder of fixture files, writes one PNG per tab and exits; the overlay's panel gets the same through a test host. CI runs it for English, German and one CJK language at 100 % and 150 % and keeps the PNGs as artefacts.
14. **Settings that change the result count in the multiplayer hash and are locked in a multiplayer game** (below).

### Settings and the multiplayer hash

The overlay's multiplayer code is the start of a SHA-256 over `<plugin>[.<module>] <version>` of what changes the game and acts in the session (design §13, §15); players compare it by hand. Settings are not in it. A setting of a module that changes the game can change the result: today's plugins that change the game have settings that do (Lodestone's `flip_ratio`, `cooldown_months`) and settings that do not (Smithy's keys, Lodestone's `log_flows`). Two players with the same code and different values of the first kind run different simulations, and a `restart = false` value changed in the overlay mid-session diverges at once. No such plugin offers multiplayer today (Lodestone does not; Smithy's modules post the game's own commands, which every machine runs alike), so this has not happened yet [code: the manifests read for the prototype]. Decided:

- **Which settings count.** A setting of a plugin or module that changes the game counts for the game unless it says `affects_gameplay = false` (keys, logging, drawing). `key` settings default to `false`; `anvil check` asks for the key on the others of a plugin or module that offers multiplayer.
- **The hash.** The values in effect of counting settings join their owner's line (`lodestone <version> cooldown_months=24 flip_ratio=1.5 …`, every counting setting, names sorted), so players with different values see different codes. A `restart = true` value changed for the next start does not count until then.
- **The lock lasts the multiplayer session**, from its start (a hosted game starting, a save loading, a hot join) to its end: the overlay shows counting settings disabled with "locked in a multiplayer game", and `anvil.control` refuses them. Ironman alone locks nothing.
- **The lobby is before the session**, so counting settings can still change there. The game has no session of its own until it starts: the root holds the front end, whose states include the nation selection (design §13.1, point 3). That the multiplayer lobby is a front-end state was not checked in a multiplayer game [hypothesis]. The players settle the values in the lobby, and so the overlay shows the code outside a session too: "Multiplayer code for a game started now: XXXX-XXXX-XXXX-XXXX", computed from the multiplayer opt-ins and the values in effect, the same as the session will compute it. In the session it shows the session's code, as today. Players compare it in the lobby and again after the start.

## Compatibility

- **Older Anvil.** `module`, `advanced`, a module's `group`, `[retired.*]` and a setting's `affects_gameplay` are unknown keys there, so an older Anvil skips the plugin (design §5.3). A plugin that uses them declares `anvil = ">=<the release with them>"`, as for any added key (CONTRIBUTING).
- **API 2.** No host function changes. `AnvilControlSetting` and the module entry of `anvil.control` grow appended fields (the module index, `advanced`, the module's group), and the service grows the write calls of point 7; the overlay is the only caller.
- **`anvil.toml`.** No new keys. The overlay writes the same text the Manager writes.
- **Players' files.** Unchanged, except the one-time move of point 4 and the new `last-start.toml`.

## Considered options

- *Keep settings and modules apart, linked by name convention* (a setting named as its module, or prefixed by it). The prototype guessed the links that way [prototype] and needed per-plugin exceptions (Smithy's `drill_key` belongs to `drill_all`, `picture_prefix` to `trade_pop_icons`). A convention cannot be checked.
- *Let a module carry its own settings in `plugin.toml`.* Moves settings out of `settings.toml`, which the generated accessors (§16), the environment overrides and the translations read.
- *A settings switch for each module* (Bellows on `main`). Two switches for one feature, and only the core's switch keeps the multiplayer hash and the suspension true (ADR 0011, "Release").
- *Each plugin migrates its retired settings itself.* The plugin would write `anvil.toml`, a second writer, and the module would still be on at that start because the core resolved modules before the plugin ran. Rejected for point 4.
- *The Manager writes while the game runs.* Two writers would need locking and a rule for which wins; the overlay already is where the player is.
- *A switch for a group of modules*, *turning off what depends on a plugin*. Left out: a player turns one thing at a time, and switches are kept, not changed for the player.
- *No record of the last start*; the Manager marks nothing while the game is closed. Rejected: undo and the pending count would work only in the overlay.

## Consequences

- The Manager loses its Settings and Mods tabs (Mods subject to point 10); the overlay's Status, Settings and Mods tabs become one Plugins tab. Both draw from the model of point 9.
- Bellows 2.0 drops its mode settings, moves its timing profiles and self-checks into one "Diagnostics" module off by default, and retires the mode settings by point 4, so it needs the Anvil release with this ADR (eu4-engine-lab `docs/bellows-2-module-layout-plan.md`). Tongs' `game_calls_ironman` and `game_calls_multiplayer` are a second gate inside the plugin's opt-in, which also covers its inputs [code: tongs `plugin.toml`, `settings.toml`]; as a `game_calls` module with its own opt-ins (ADR 0011) they become the core's and retire by point 4. Smithy's module names become short names. Each is its own pull request in its repository, after Anvil's.
- The plugin template and `anvil check` gain the new keys; the guidelines' §6 is what plugin authors read.
- Order of work: this ADR and the guidelines; the core (points 1 to 8); the model (point 9); the Manager; the overlay; the screenshot mode with the first UI pull request; then the plugins, released together with Anvil as one bundle.

## Limits

- Nothing of this is built. The prototype shows the UI on real manifests with guessed `module` keys and two sample plugins from mods; no game was started for this ADR.
